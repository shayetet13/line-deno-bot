```
ถ้าข้อความมี job ID  → jobKey = "id:" + <jobId>
ถ้าไม่มี job ID      → jobKey = hash(sourceMessageId + senderId + roomId + ruleId)
```

## 7. เป้าหมายเวลา (budget — ยังไม่พิสูจน์)

> ⚠️ **ตารางนี้ต้องแก้** — วัดจริงบน Tokyo server:
>
> - **push stream** เห็นข้อความช้า ~123–126 ms (เวลาภายในของ LINE, network RTT แค่ 0.4 ms)
> - **dedicated poll** (`fetchSquareChatEvents`) เห็นเร็วกว่า ~40–100 ms → race แล้ว inbound ลงมา **p50
>   58 ms / min 24 ms** (n=5, ห้องเฝ้า) ⇒ inbound **ลดได้** ด้วย receive-path race (Phase 5)
> - inbound ก่อนหน้านี้เข้าใจว่า ~126 ms fixed และเวลานั้นเกือบทั้งหมดเป็น **เวลาภายในของ LINE** ที่โค้ดเราลดไม่ได้
>   (network RTT ถึง LINE = 0.4 ms) ดู `phase-plan.md` หัวข้อ "ผลวัดจริงบน Tokyo server"
>
> เป้าที่ควรใช้แทน: แยก **ส่วนที่ LINE คุม** (inbound, วัดเพื่อ monitor ไม่ใช่เพื่อ optimize) ออกจาก **ส่วนที่เราคุม**
> (our processing + send RTT) แล้วตั้งเกณฑ์ผ่าน/ตกเฉพาะส่วนหลัง

| ค่า                                               |      เป้า | เกณฑ์ปฏิบัติ                                 |
| ------------------------------------------------ | -------: | ---------------------------------------- |
| Inbound (event time → payload พร้อม decode)       |  ≤ 11 ms | budget                                   |
| Our processing (decode+match+sequence+serialize) | ≤ 0.5 ms | **hard gate Phase 4**                    |
| LINE send (submit → decode ACK)                  |  ≤ 19 ms | guardrail 23 ms (Playbook §7.10)         |
| Event-to-ACK                                     |  ≤ 32 ms | SLO + error budget ไม่ใช่ hard fail รายครั้ง |
| First-response win rate                          |     สูงสุด | ต้องมีนิยามผู้ชนะจากข้อ 4 ก่อน                  |
